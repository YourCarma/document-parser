## 3. Блокер Н-1 — ЗАКРЫТ (проверено на живом брокере)

**Был:** публикация копии в DLQ/retry шла через default exchange. Если очереди
физически нет, брокер отвечает `basic.ack`, `publish()` не бросает, код считал
копию сохранённой и подтверждал оригинал — сообщение исчезало.

**Стало:** `_publish_copy` публикует с `mandatory=True` и считает успехом
**только `Basic.Ack`**. Проверено фактически на aio-pika 9.6.2:

| Публикация | Результат |
| --- | --- |
| `mandatory=False`, очереди нет | `Basic.Ack` — ошибки нет |
| `mandatory=True`, очереди нет | **не бросает**, возвращает `Basic.Return` |
| `mandatory=True`, очередь есть | `Basic.Ack` |

Живая проверка сценария (временная топология, DLQ удалена после `connect()`):
`Basic.Return` пойман → `CRITICAL` → оригинал **не подтверждён** →
`_dlq_ready=False` → после закрытия соединения сообщение вернулось в очередь
(`ready=1`).

**Ловушка замера, на которую я сам попался:** `queue.declare(passive=True)` на
**том же канале** отдаёт закэшированный `declaration_result` и показывает старый
`message_count`. Проверено отдельно: тот же канал → 0, свежее соединение → 1.
Для проверки очередей в тестах на живом брокере пользуйтесь management API
(`:15672`) или новым соединением, иначе получите ложный вывод «сообщение
потеряно».

## 4. Главный урок этих двух дней

Три дефекта одного класса, и все три — **тихая потеря сообщения**:

1. dead-letter уходил с routing key, на который нет биндинга → сообщение
   уничтожалось;
2. публикация в несуществующую очередь при выключенном объявлении топологии
   проходила молча;
3. Н-1 — то же самое, но для DLQ на живом сервисе.

Ни один не ловился юнит-тестами на фейках. Все три нашлись только прогоном
против живого RabbitMQ. **Вывод на будущее: любые изменения в консюмере
проверять на живом брокере**, фейки здесь систематически врут в одну сторону.

## 6. Вопросы, которые нужно закрыть с командой гейтвея

Ни один не блокирует разработку, но все три блокируют **включение в прод**:

1. ~~`consumer_timeout`~~ — **решено**, см. §9. Поднимаем на брокере до 60 минут,
   приложение выставлено под это значение.
2. **Написание имени сервиса в ключе задачи.** Ключ — `{user_id}:{service}:{task_id}`,
   средний сегмент берётся из `SERVICE_NAME`. Везде проставлено `document-parser`
   через дефис, по аналогии с именами очереди и exchange, но это догадка.
   Ошибка тихая: обновления уйдут по несуществующему ключу и задача внешне
   зависнет на нуле. На старте сервис логирует собранный формат ключа — сверить
   с тем, что кладёт гейтвей.
3. **У рабочей очереди нет и не будет DLX** — она чужая. Поэтому копии в DLQ
   публикует сам сервис. Следствие для эксплуатации: `document-parser.dlq`
   наполняется только работающим подом, и нужен алерт на её непустоту.

## 7. Что операторам сделать руками перед деплоем

1. **Удалить существующую `document-parser.retry`**, если она создана прежней
   версией: аргументы изменились на `x-dead-letter-exchange=""` +
   `x-dead-letter-routing-key=document-parser.queue`. Иначе объявление даст
   `PRECONDITION_FAILED`, сервис поднимется, но повторы уйдут в деградацию.
2. **Права пользователя RabbitMQ на configure** для `document-parser.dlx`,
   `document-parser.dlq`, `document-parser.retry`. Без них сервис стартует, но
   работает в деградации — видно в стартовом логе `Broker: топология готова`.
3. `document-parser.tasks` и `document-parser.queue` должны существовать **до**
   старта пода — их создаёт гейтвей, сервис их не создаёт принципиально.
4. `--timeout-graceful-shutdown` в деплойменте воркера ≥ `RMQ_SHUTDOWN_GRACE_SECS`.
5. Ресурсы под `prefetch=3`: `PARSER_WORKERS=3`, лимит памяти считать от трёх
   параллельных docling-парсингов.

## 9. consumer_timeout: что сделано и что осталось сделать руками

**Факт:** на `sys-dev-rabbitmq-1` (образ `rabbitmq:4.0-management`)
`consumer_timeout` явно не задан и равен дефолтным **30 минутам**
(`{ok,1800000}` из `rabbitmqctl eval`). Перевод большого документа это время
превышает: канал рвётся с `PRECONDITION_FAILED`, сообщение возвращается и
переигрывается по кругу.

**Решение:** поднять на брокере до 60 минут. Приложение уже приведено к этому
значению: `TASK_TIMEOUT_SECS=3000` (50 минут), `RMQ_ACK_DEADLINE_SECS=3600`,
запас 600 с при требуемых `RMQ_ACK_SAFETY_MARGIN_SECS=120`.

**Осталось сделать руками** — в `/mnt/sda/Development/DevDeployment/sys-dev/rabbitmq/rabbitmq.conf`
(bind-mount в контейнер) дописать строку:

```ini
# Максимальное время, которое сообщение может оставаться неподтверждённым.
# Перевод документа идёт десятки минут; дефолтных 30 минут не хватает.
consumer_timeout = 3600000
```

Значение в **миллисекундах**. Затем `docker compose restart rabbitmq` —
параметр читается только при старте. Проверка:

```bash
docker exec sys-dev-rabbitmq-1 rabbitmqctl eval 'application:get_env(rabbit, consumer_timeout).'
# ожидаем {ok,3600000}
```

Если решите поставить другое значение — поправьте `RMQ_ACK_DEADLINE_SECS` в
env-файлах, чтобы стартовая валидация не врала. На логику она не влияет,
только на предупреждение в логе.
