## 1. Короткий вывод

Асинхронный конвейер перевода уже существует целиком — это
`app/modules/translator/v2/`. Он умеет всё, что нужно очереди: бакет через
`resource_manager`, upload и share-ссылки через `watchtower`, прогресс и
`response_data` в `webhook_manager`, парсинг в пуле процессов, перевод под
общим семафором.

Поэтому задача — не «написать новый пайплайн», а:

1. добавить новый **транспорт** (consumer RabbitMQ) рядом с HTTP-роутером;
2. сделать источник файла подменяемым (`UploadFile` **или** скачивание из
   `watchtower` по `file_path`);
3. добавить **отмену** — сейчас её нет ни в каком виде; модель кооперативная
   (§6), парсинг доигрывается до конца;
4. добавить в `watchtower`-клиент метод **download**;
5. попутно закрыть долги текущей реализации — они перечислены в §10 и часть из
   них под нагрузкой из очереди станет заметно опаснее, чем под HTTP.

## 3. Факты из OpenAPI смежных сервисов

Спеки вычитаны 2026-08-13 с dev-контура.

### 3.1 `task_gateway` (`:10008`, v1.0.0)

- `POST /api/v1/broker/publish` — тело `{task_type, payload, user_id?}`,
  заголовок `x-user-id` приоритетнее `payload.user_id`.
- Ответ: `{"task_key": "user_id:service_name:task_uuid"}`.
- `POST /api/v1/tasks/cancel?task_id=...` — отмена задачи.

Из описания эндпоинта: задача публикуется в брокер **и регистрируется в state
manager**. То есть `task_gateway` создаёт запись задачи сам — из очереди мы её
**не создаём**, а только обновляем.

### 3.2 `webhook_manager` (`:10001`, v1.0.1)

- `GET /api/v1/storage/task?key={user_id}:{service}:{task_id}` → `Task`.
- `PATCH /api/v1/storage/update_progress`, `PATCH /api/v1/storage/update_response_data` — уже используем.
- **`TaskStatus` в спеке: `PENDING | AWAITING | PROCESSING | READY | ERROR | CANCELLED`.**

У нас в `app/modules/webhook_manager/schemas.py:8-13` перечисления `CANCELLED`
нет. Именно оно и есть механизм отмены.

### 3.3 `resource_manager` (`:2899`, v0.2.6)

`servers: [{url: "/api/v1"}]` → реальный путь `/api/v1/resource/` с обязательным
заголовком `x-user-id`. Текущий клиент делает ровно это, менять не нужно.

### 3.4 `watchtower` (`:2893`)

```
POST /api/v1/cloud/{bucket}/file/download
body: {"file_name": "documents/report.pdf"}    // form.DownloadFileForm
200 -> байты файла
```

Есть также `POST /api/v1/cloud/{bucket}/file/attributes` (`{"file_path": ...}`) —
можно проверить существование и размер до скачивания.

Расхождение имён полей (`file_name` при скачивании, `file_path` при share и
attributes) — так в спеке, не опечатка документа.

### 3.5 Фактическая топология dev-брокера (снято 2026-08-13)

Проверено напрямую на живом RabbitMQ, а не по договорённостям:

| Объект | Факт |
| --- | --- |
| exchange `document-parser.tasks` | существует, тип **`direct`**, `durable=true` |
| биндинг | `document-parser.tasks` → `document-parser.queue`, ключ **`document-parser.translate`** (точный) |
| очередь `document-parser.queue` | существует, `arguments={"x-queue-type": "classic"}`, **без `x-dead-letter-exchange`** |

Три следствия, каждое стоило бы прода:

1. **Exchange не `topic`, а `direct`.** План исходил из `topic` — исправлено везде.
   На `direct` шаблоны `#` и `*` не работают: подписка возможна только на точные
   ключи, и любой routing key, на который нет биндинга, приводит к **молчаливому
   уничтожению** сообщения.
2. **Очередь и exchange — чужие, мы их не создаём.** Подтверждено заказчиком:
   «очередь создаётся заранее», владелец — `task_gateway`. Активное объявление с
   нашими аргументами падало бы с `PRECONDITION_FAILED` (очередь уже создана с
   другими), то есть воркер не стартовал бы вовсе. Поэтому чужие объекты
   (exchange, рабочая очередь, её биндинг) не объявляем и не биндим — только
   потребляем; свои служебные (retry-очередь, DLX, DLQ) объявляем сами.
3. **У рабочей очереди нет DLX, и добавить его мы не можем** — она чужая.
   Значит `reject(requeue=False)` не откладывает сообщение в DLQ, а
   **уничтожает** его, и ветка «permanent ошибка → DLQ» из §5.7 на
   dead-lettering не строится. Решение: на permanent-ошибке **публикуем копию в
   наш DLQ явно** и только после успешной публикации подтверждаем оригинал.
   Порядок важен: сначала сохранили копию, потом ack — иначе сбой публикации
   означает потерянное сообщение. Не удалось опубликовать — не подтверждаем,
   пусть переиграется.

Конверт сообщения подтверждён живым экземпляром из очереди: `task_id`, `user_id`
(строка), `task_type`, `payload` — ровно как в §4.1. AMQP-заголовков нет,
`message_id` и `correlation_id` не заполнены, то есть **`task_id` доступен только
из тела**.

## 4. Контракт сообщения

### 4.1 Конверт (подтверждён примером из очереди)

```json
{
  "task_id": "5fb0b68c-2259-47d8-8e72-3dc517ac6d4d",
  "user_id": "1234",
  "task_type": "document-parser.translate",
  "payload": { }
}
```

Важные следствия:

- **`task_id` и `user_id` лежат на верхнем уровне**, `payload` —
  сервис-специфичный. Схемы делим на две: `TaskEnvelope` (общая) и payload
  конкретного `task_type`.
- В примере от гейтвея `payload` может содержать **свой** `user_id`, причём
  отличающийся от верхнеуровневого (`"1234"` vs `21233`). Правило: **верхний
  уровень главнее**, `payload.user_id` используем только если верхнего нет.
  Это повторяет логику самого гейтвея (заголовок важнее тела).
- `user_id` — всегда строка, приведение типов не требуется.
- Ключ для `webhook_manager` собираем как `{user_id}:{service}:{task_id}`, где
  средний сегмент — `settings.SERVICE_NAME`. Отдельную переменную не заводим, но
  значение в env обязано совпадать с тем, которое использует гейтвей: во всех
  трёх env-файлах проставлено `document-parser` через дефис, по аналогии с
  именами очереди и exchange — **это догадка, её нужно подтвердить у гейтвея**.
  Ошибка здесь тихая: обновления уйдут по несуществующему ключу, задача внешне
  «зависнет» на нулевом прогрессе. Стоит на старте один раз залогировать
  собранный `task_key` — это дёшево и сразу вскроет расхождение.

### 4.2 Payload для `document-parser.translate`

Исходный вариант из постановки был `user_id / source_language / target_language /
file_path / error`. Правки:

- `user_id` переезжает на верхний уровень конверта (он там уже есть);
- **`error` убираем** — это поле результата, а не задачи. Продюсер его не
  присылает, а наружу ошибка уходит через `response_data.error` в
  `webhook_manager`, где поле уже есть;
- добавляем флаги парсера — HTTP-ручка их принимает, очередь не должна быть
  беднее;
- добавляем `output_prefix` — сейчас v2 кладёт результат в корень бакета
  (`prefix=""`), одноимённые файлы затирают друг друга.

```json
{
  "task_id": "5fb0b68c-2259-47d8-8e72-3dc517ac6d4d",
  "user_id": "1234",
  "task_type": "document-parser.translate",
  "payload": {
    "file_path": "documents/report.pdf",
    "source_language": "auto",
    "target_language": "ru",
    "bucket": null,
    "output_prefix": "translated",
    "parse_images": false,
    "include_image_in_output": false,
    "full_vlm_pdf_parse": false
  }
}
```

- `file_path` — **object key внутри бакета** (без `/api/gateway`, подтверждено).
- `bucket` — необязательное явное переопределение; при `null` берём персональный
  Document-бакет через `resource_manager`.
- Языки прогоняем через тот же ISO-639-валидатор, что и `TranslatorRequest`
  (`modules/translator/v1/schemas.py:38`), включая поддержку `auto`.

### 4.3 Что отдаём наружу

В очередь ничего не публикуем — результат живёт в `webhook_manager`:
`progress`/`status` + `response_data` (`TranslatorResponseData`). Push о
завершении обратно в брокер — отдельная задача, в текущий объём не входит.

## 5. Архитектура модуля брокера

Каталог по стилю остальных модулей (`abc/` + фабрика, как у парсера):

```
app/modules/broker/
├── __init__.py
├── abc/
│   ├── abc.py         # BrokerConsumerABC
│   └── factory.py     # BrokerFactory: BROKER_TYPE -> реализация
├── rabbitmq/
│   ├── consumer.py    # RabbitMQConsumer(BrokerConsumerABC) на aio-pika
│   └── config.py      # разбор env
├── dispatcher.py      # реестр task_type -> handler
├── schemas.py         # TaskEnvelope, TaskType, payload-схемы
└── handlers/
    └── translate.py
```

### 5.1 Абстракция

```python
class BrokerConsumerABC(ABC):
    @abstractmethod
    async def connect(self) -> None: ...
    @abstractmethod
    async def start(self) -> None: ...      # начать потребление
    @abstractmethod
    async def stop(self) -> None: ...       # graceful: дождаться активных задач
    @abstractmethod
    async def health(self) -> bool: ...
```

В базовый класс не выносим ничего AMQP-специфичного (exchange, routing key,
prefetch) — иначе Kafka/NATS в абстракцию не влезут и смысл пропадёт. Это живёт
в `rabbitmq/config.py`.

### 5.2 Диспетчер

Тонкий реестр, чтобы новые типы задач не трогали код консюмера:
`dispatcher.register(TaskType.TRANSLATE, TranslateHandler)`. Консюмер: распарсил
конверт → нашёл handler по `task_type` → вызвал. Неизвестный `task_type` → лог +
`reject(requeue=False)` (в DLQ), не бесконечный requeue.

### 5.3 Библиотека

**`aio-pika`** (`connect_robust` с авто-переподключением). `pika` синхронная —
для asyncio-приложения не подходит. В `pyproject.toml`: `aio-pika = "^9.5"`.

### 5.4 Где запускать консюмер

**Рекомендация: в lifespan того же приложения за флагом `BROKER_ENABLED`.**
Один образ, две роли: `true` в deployment воркера, `false` — в deployment API.
Так переиспользуются `http_session`, `executor` и семафоры.

Инициализацию ресурсов при этом полезно вынести из lifespan в отдельный модуль
(`app/runtime.py`) — тогда отдельный entrypoint `app/worker.py`, если он
понадобится для независимого масштабирования, будет стоить десяток строк.

### 5.5 Параллелизм: три документа одновременно

`prefetch_count = 3` — три сообщения в работе на реплику. Из этого следуют
требования к ресурсам, которые нужно выставить явно, иначе параллелизм будет
только на бумаге:

- **`PARSER_WORKERS >= 3`.** Парсинг ограничен `parser_semaphore`, а в `.env.dev`
  сейчас `PARSER_WORKERS=2` — третья задача просто встанет в очередь на семафоре.
  Для деплоймента воркера ставим 3 (или 4, чтобы был запас на короткие задачи).
- **Память.** Три docling-парсинга одновременно — это три набора моделей и три
  копии документа в памяти. Под тяжёлые PDF (особенно `full_vlm_pdf_parse`)
  лимит контейнера надо считать от трёх параллельных парсингов, а не от одного.
  Если памяти впритык — честнее держать `prefetch=2`, чем ловить OOM.
- **OOM бьёт по всем троим.** Убитый OOM-killer'ом воркер пула роняет не только
  свою задачу, но и две соседние, и ломает пул навсегда (проверено, см. §10,
  P0-1). При `prefetch=3` это перестаёт быть теоретическим риском — **починка
  P0-1 обязательна до включения консюмера**.
- **Переводчик.** `TRANSLATOR_MAX_CONCURRENCY` — общий лимит **на процесс**, а
  не на задачу: три документа поделят одни и те же 5 слотов (значение из
  `.env.dev`), и каждый будет переводиться примерно втрое медленнее. Если сервис
  перевода выдерживает — поднять до 12-15 на воркер-деплоймент. Это решение про
  нагрузку на чужой сервис, поэтому согласовать, а не менять молча.

### 5.6 Ack и таймауты

- **Ручной ack** — после публикации терминального статуса (`READY` / `ERROR` /
  `CANCELLED`).
- Обработка каждого сообщения — в отдельной `asyncio.Task`, чтобы долгая задача
  не блокировала heartbeat соединения. Число одновременных задач ограничено
  `prefetch_count`.
- **Грабли, о которые спотыкаются все: `consumer_timeout` в RabbitMQ.** Начиная
  с 3.8.15 брокер по умолчанию закрывает канал с `PRECONDITION_FAILED`, если
  сообщение не подтверждено за **30 минут**. Перевод большого документа это время
  превышает легко — и тогда канал рвётся, сообщение возвращается в очередь и
  обрабатывается заново, бесконечно. **Решено:** делаем оба — `consumer_timeout`
  на брокере поднимается до 60 минут (`consumer_timeout = 3600000` в
  `rabbitmq.conf`), таймаут задачи 50 минут (`TASK_TIMEOUT_SECS=3000`).
  Фактическое значение на нашем RabbitMQ проверено: до правки там дефолтные
  30 минут (`{ok,1800000}`).
- При SIGTERM: сначала stop consuming, потом дождаться активных задач с
  таймаутом, потом закрывать соединение. Не успевшие — без ack, брокер их
  вернёт.

### 5.7 Классификация ошибок

Правило простое: **что не починится повторной попыткой — выкидываем из очереди
и пишем в `webhook_manager`**; что может починиться — ретраим ограниченное число
раз, потом в DLQ.

| Ситуация | Очередь | `webhook_manager` |
| --- | --- | --- |
| Конверт не разобрался (не JSON, нет `task_id`/`user_id`) | `reject`, DLQ | **писать некуда** — ключа нет, только лог + метрика |
| Неизвестный `task_type` | `reject`, DLQ | `ERROR`, «Неизвестный тип задачи» |
| Payload не прошёл валидацию (нет `file_path`, плохой код языка) | `reject`, DLQ | `ERROR`, «Неверный формат данных задачи» |
| Формат файла не поддерживается | `reject`, DLQ | `ERROR`, «Формат файла не поддерживается» |
| Файл не найден в бакете (404) | `reject`, DLQ | `ERROR`, «Файл не найден в хранилище» |
| Нет персонального бакета у пользователя | `reject`, DLQ | `ERROR`, «Не найдено хранилище пользователя» |
| Файл больше лимита | `reject`, DLQ | `ERROR`, «Файл слишком большой» |
| Документ битый, парсинг упал | `reject`, DLQ | `ERROR`, «Не удалось обработать документ» |
| Таймаут парсинга / всей задачи | `reject`, DLQ | `ERROR`, «Превышено время обработки» |
| Upstream недоступен (5xx, connection error) | `nack(requeue)`, до `RMQ_MAX_RETRIES`, затем DLQ | `ERROR` только после исчерпания попыток |
| Отмена | `ack` | `CANCELLED` |
| Процесс воркера умер во время обработки | сообщение вернётся само (нет ack) | статус останется `PROCESSING`, задача переиграется |

Пояснения к неочевидному:

- **Первая строка — единственный случай, когда мы не можем ничего сообщить
  пользователю.** Без `task_id` и `user_id` ключ не собрать. Такие сообщения
  должны быть заметны: отдельный лог-уровень и алерт на непустой DLQ, иначе
  задачи будут тихо исчезать.
- Технический текст исключения наружу **не отдаём** — в `response_data.error`
  идёт человекочитаемое сообщение из таблицы, детали только в лог. Механика
  уже есть: `_STAGE_MESSAGES` / `_stage_to_user_message` в
  `translator/v2/service.py:24-36`, её и переиспользуем, дополнив классами ошибок
  очереди.
- Повторная обработка (последняя строка) **не идемпотентна**: оригинал зальётся
  в бакет второй раз поверх первого. Для одинакового имени это перезапись тем же
  содержимым — терпимо, но если появится префикс с `task_id`, всё станет чисто
  автоматически (см. P1-6).
- «Выкинуть из очереди» = **опубликовать копию в `document-parser.dlq` и затем
  подтвердить оригинал**. На dead-lettering через `reject(requeue=False)` здесь
  положиться нельзя: у рабочей очереди нет DLX и добавить его мы не можем (§3.5).
  Сообщение не теряется совсем, а откладывается для разбора.

## 6. Отмена задачи

Модель — **кооперативная**: сервис периодически смотрит статус задачи и, увидев
`CANCELLED`, аккуратно выходит из пайплайна. Насильно прерывать этапы не
пытаемся (обоснование и отложенный вариант — в приложении §13).

### 6.1 Как узнаём

`GET /api/v1/storage/task?key=<task_key>` → `task.progress.status == "CANCELLED"`.
Отмену инициирует клиент через `task_gateway /api/v1/tasks/cancel`, тот ставит
статус в state manager. Мы — **читатель**, не инициатор.

Подготовка: `CANCELLED` в `TaskStatus` + `get_task(key)` в клиенте.

### 6.2 Как проверяем

```python
class CancellationToken:
    def __init__(self, webhook, key, ttl_secs: float = 5.0): ...
    async def is_cancelled(self) -> bool: ...
    async def raise_if_cancelled(self) -> None:  # -> TaskCancelled
```

- Кэш на TTL обязателен: без него проверка «на каждом прогоне» в цикле перевода
  даст сотни лишних HTTP-запросов на один документ. С TTL=5 c и тремя
  параллельными задачами нагрузка на `webhook_manager` — меньше запроса в
  секунду.
- Ошибка запроса статуса **не считается отменой** — логируем и продолжаем, иначе
  моргнувший `webhook_manager` убьёт все живые задачи.

### 6.3 Где проверяем

1. Сразу после получения сообщения — задачу могли отменить, пока она лежала в
   очереди. Самая дешёвая и самая частая экономия: работа не начинается вообще.
2. На границе каждого этапа: скачивание → парсинг → перевод → upload.
3. Внутри цикла перевода, между батчами (`_translate_in_batches`). Точка
   естественная: там уже есть цикл и уже публикуется прогресс.

Задержка реакции = TTL опроса + время до ближайшей точки проверки:

| Этап | Ближайшая точка | Типичная задержка |
| --- | --- | --- |
| ожидание в очереди | до старта | мгновенно |
| скачивание файла | после этапа | секунды |
| **парсинг** | после этапа | от секунд до минут — весь парсинг доигрывается |
| перевод | между батчами | ≤ время одного батча |
| upload результата | после этапа | секунды |

**Осознанный компромисс:** отмена во время парсинга сработает только по его
завершении, потому что docling уходит в длинный вызов без точек проверки, а
прервать его можно лишь убийством процесса. Для обычных документов это секунды.
Хвост — тяжёлые PDF, особенно с `full_vlm_pdf_parse`, где парсинг идёт минутами;
именно там пользователь и заметит, что «отмена не сработала сразу».

Ограничитель на этот хвост нужен в любом случае: `PARSE_TIMEOUT_SECS` задаёт
верхнюю границу и для зависшего парсинга, и для задержки отмены. Если по факту
окажется, что жалобы на «долгую отмену» есть — включаем вариант из §13, он
ложится сверху и не требует переделки остального.

### 6.4 Что делаем при отмене

`raise TaskCancelled` → отдельная ветка перехвата →

- статус `CANCELLED`, `text_status` = «Задача отменена», `progress` **не
  обнуляем** (видно, где остановились);
- `error` не заполняем — отмена не ошибка;
- `finally` чистит временные файлы (уже реализовано);
- сообщение **ack**-аем — переигрывать нечего;
- загруженный оригинал в бакете не удаляем (обсуждаемо, вопрос №4).

Критично: `except Exception` в `translator/v2/service.py:166-176` пишет
`status=ERROR, progress=0`. `TaskCancelled` надо ловить **до** него, иначе
отменённая задача превратится в упавшую.

Ещё одно место, где легко потерять статус: при остановке сервиса (SIGTERM)
незавершённые задачи отменяются уже через `asyncio.Task.cancel()`, а после него
любой `await` в `except`/`finally` немедленно снова получает `CancelledError` —
то есть «на выходе опубликуем статус» тихо не сработает. Терминальный статус в
этом сценарии публикуем под `asyncio.shield()` либо не публикуем вовсе: без ack
сообщение вернётся в очередь и задача переиграется на другой реплике, что даже
правильнее.

## 7. Скачивание исходного файла

`file_path` — object key внутри бакета, поэтому вариант ровно один:

```python
async def download_file(self, bucket: str, file_path: str, dest_dir: str) -> str:
    """POST /api/v1/cloud/{bucket}/file/download {"file_name": file_path} -> локальный путь."""
```

Требования:

- **Стримить в файл** (`resp.content.iter_chunked`), не `await resp.read()` —
  воркер и так держит docling-пайплайн в памяти.
- Имя локального файла — из `Path(file_path).name`, **расширение обязано
  сохраниться**: `ParserFactory` выбирает парсер по суффиксу
  (`parser/v1/abc/factory.py:44`).
- Ограничение размера (`MAX_DOWNLOAD_FILE_SIZE_MB`) с внятной ошибкой.
- Проверка расширения по поддерживаемым форматам **до** скачивания: HTTP-ручка
  валидирует MIME валидатором схемы, очередь не должна быть слабее.
- Скачивать во временный каталог задачи и удалять его в `finally`.

## 8. Рефакторинг translator v2 под два транспорта

Один пайплайн, два входа. Минимально инвазивный путь:

1. Вынести «получение исходного файла» в стратегию:

```python
class SourceFileProvider(Protocol):
    async def acquire(self) -> tuple[str, str]:  # (local_path, original_filename)
```

   - `LocalUploadSource` — то, что делает HTTP-роутер сейчас (`save_file`);
   - `WatchtowerSource` — скачивает по `bucket` + `file_path`.

2. Разделить `run_translation_task` на «подготовку» (бакет, исходный файл,
   upload оригинала — различается) и «ядро» (парсинг → перевод → экспорт →
   upload результата → статусы — общее).

3. Прокинуть `CancellationToken`; для HTTP-сценария — no-op токен, чтобы не
   плодить ветвления.

4. Из очереди **не создавать** задачу в `webhook_manager` — она создана
   гейтвеем. `create_task` остаётся только у HTTP-входа.

Инварианты, которые нельзя ломать (подробности в `translator/v2/AGENTS.md`):
`quote_fields=False` в multipart, общий `http_session`, общие семафоры,
`_make_copy_with_refmode` при экспорте.

Разбор `translator/v2` и его зависимостей. Приоритеты: **P0** — чинить до

### Детали по P0

**1. Пул процессов не восстанавливается после падения воркера.**
`app.state.executor` создаётся один раз в lifespan. Если процесс-воркер умрёт
(OOM на тяжёлом PDF — реальный сценарий для docling), `ProcessPoolExecutor`
переходит в `BrokenProcessPool` **навсегда**. Проверено экспериментом (§13):
гибель одного воркера роняет и **соседние** выполняющиеся задачи, и все
последующие. Под HTTP это заметят и передеплоят; консюмер же будет молча
вычерпывать очередь, переводя все задачи в `ERROR`.

При `prefetch=3` это перестаёт быть редким сценарием: три docling-парсинга
одновременно — самый вероятный повод для OOM-killer'а, а цена одного убитого
воркера — три погибшие задачи и мёртвый пул до перезапуска пода.

Лечение: ловить `BrokenProcessPool` и пересобирать `app.state.executor` под
`asyncio.Lock` (идемпотентно, с логом и метрикой), а задачи, погибшие вместе с
пулом, возвращать в очередь через `nack(requeue=True)` — они не виноваты.
Радикальный вариант (процесс на задачу, общего пула нет вовсе) описан в §13 и
сейчас отложен вместе с жёсткой отменой.

**2. Транзиентный сбой `webhook_manager` уничтожает результат.**
`_update` вызывается в основном потоке выполнения (строки 92, 103, 122, 142,
156) и любое исключение из него выбрасывается наружу, в общий `except`. То есть
если после 20 минут перевода на шаге «95% — загружаю переведённый файл»
webhook-менеджер моргнул — задача помечается `ERROR`, а переведённый файл
удаляется в `finally`. Работа выброшена из-за сбоя в отчётности.
Нужно: ретраи с backoff внутри клиента `webhook_manager`, а публикацию
**промежуточных** статусов сделать best-effort (как уже сделано в цикле
перевода, `service.py:290-297`) — падать имеет смысл только на терминальном
статусе, и то предварительно ретраясь.

**3. LibreOffice без таймаута блокирует воркер навсегда.**
`convert_doc_to` (`utils.py:141`) вызывает `subprocess.run` без `timeout=`.
`soffice` славится зависаниями на битых `.doc`. Зависший вызов держит процесс
пула вечно; при `PARSER_WORKERS=3` трёх таких документов достаточно, чтобы
сервис перестал парсить что-либо вообще — а из очереди битый документ будет
приходить снова и снова.

Нужен `SOFFICE_TIMEOUT_SECS` и убийство по нему. Важная деталь, проверенная
экспериментально (§13): `subprocess.run(timeout=)` убивает только прямого
потомка, а всё, что `soffice` успел породить, остаётся сиротой и продолжает
жить. Правильно — `Popen(..., start_new_session=True)` и `os.killpg` по
таймауту.

**4. Ошибка 4xx на одном элементе убивает весь документ.**
`translate_tracked` (`service.py:267`) ловит только `TimeoutError` и
`RetryableUpstreamError`. Но `post_request` (`translator/v1/utils.py:38-45`)
для статусов < 500 бросает обычный `HTTPException`, а `translate_element`
(`translator/v1/service.py:78`) — `ValueError` при неожиданном формате ответа.
Ни то, ни другое не перехватывается: один странный элемент (пустая строка,
слишком длинный кусок, битая кодировка) обнуляет перевод всего документа.
Логика деградации уже есть — надо просто расширить набор перехватываемых
исключений и считать «непереведённые» элементы, вынося их количество в
`text_status`.

**5. Нет `CANCELLED`.** См. §6, отдельно чинить не нужно — закрывается этапом 1
плана.

### Детали по P1

**6. Коллизии имён в бакете.** `upload_file` вызывается с `prefix=""`
(`service.py:96,148`), файл ложится в корень персонального бакета под исходным
именем. Два перевода `отчёт.pdf` → второй затирает результат первого, включая
уже выданную пользователю share-ссылку. Предлагается префикс на задачу
(`translated/{task_id}/` или `output_prefix` из payload).

**7. Session-туннелирование.** `service.py:135` передаёт в переводчик
`http_session=self.webhook.session` — сессию достают из клиента webhook-менеджера
«потому что она там есть». Если клиент создан без сессии (как в части тестов),
`post_request` уходит в ветку `async with aiohttp.ClientSession()` и **создаёт
новую сессию на каждый переводимый элемент** — то есть на каждый абзац
документа. Сессию надо передавать в сервис явным аргументом.

**8. Нет общего таймаута задачи** (для очереди это уже P0). Задача может висеть
неограниченно долго (зависший upstream, гигантский документ). В очереди это не
просто утечка слота `prefetch`: неподтверждённое сообщение упирается в
`consumer_timeout` брокера (§5.6), после чего канал рвётся и задача уходит на
повторную обработку — по кругу, каждый раз занимая слот. Нужен
`asyncio.timeout` на весь пайплайн со статусом `ERROR`, и значение обязано быть
меньше `consumer_timeout`.

**9. `BackgroundTasks` не переживают рестарт.** Для HTTP-сценария это
осознанный компромисс (записано в `AGENTS.md`), но для очереди — нет: с ручным
ack сообщение вернётся в очередь и обработается заново, что и есть правильное
поведение. Отдельно: **HTTP-задачи стоит оставить как есть**, а не тащить их в
брокер, пока нет явного требования.

**10. `/health` всегда возвращает `Ok`** независимо от состояния зависимостей.
Как только появится консюмер, health должен отражать хотя бы состояние
подключения к брокеру, иначе k8s будет держать в проде воркер, который ничего не
потребляет.

### Что в текущей реализации сделано хорошо

Чтобы при рефакторинге это не сломать:

- батчевание перевода (`_translate_in_batches`) вместо создания корутины на
  каждый элемент документа;
- деградация вместо падения при таймауте перевода элемента;
- best-effort публикация прогресса под `asyncio.Lock` в цикле;
- `save_file` через `mkstemp` — атомарное создание, чанковая запись, безопасно
  к коллизиям имён и к большим файлам;
- `finally` с удалением обоих временных файлов;
- общие семафоры и одна `ClientSession` на процесс;
- комментарии-предупреждения в местах, где «очевидная» правка ломает поведение
  (`quote_fields=False`, двойное URL-кодирование кириллицы).

## 12. Открытые вопросы

1. **Какой `consumer_timeout` выставлен на нашем RabbitMQ?** По умолчанию 30
   минут, и перевод большого документа его превышает — канал рвётся, сообщение
   переигрывается по кругу (§5.6). Нужно либо поднять на брокере, либо
   гарантированно уложиться в `TASK_TIMEOUT_SECS`. Это единственный вопрос,
   способный сорвать запуск незаметно для тестов на мелких файлах.
2. **В каком статусе задача к моменту получения нами сообщения** (`PENDING` /
   `AWAITING`)? От этого зависит, с чего начинать шкалу прогресса.
3. **Нужен ли `X-Organization-Id`** в запросах к `watchtower`? В спеке заголовок
   опциональный, текущий код его не шлёт, но он выбирает инстанс S3 — на
   многоорганизационном контуре без него можно уехать не в тот S3.
4. **Что делать с уже загруженным оригиналом при отмене** — оставлять в бакете
   или удалять (`DELETE /api/v1/cloud/{bucket}/file`)?
5. **Куда класть результат** — `translated/{task_id}/` или `output_prefix` из
   payload? (См. P1-6.)
6. **Нужен ли `document-parser.parse`** (парсинг без перевода) сразу, или пока
   хватит `translate`? Диспетчер рассчитан на добавление без правок консюмера.
7. **Сколько реплик воркера планируется и какой лимит памяти у пода?**
   `prefetch=3` зафиксирован, но три параллельных docling-парсинга — основной
   потребитель RAM; от этого же зависит, можно ли поднимать
   `TRANSLATOR_MAX_CONCURRENCY`: лимит переводчика общий на
   процесс, и N воркеров умножают нагрузку на сервис перевода.

## 13. Приложение: жёсткое прерывание парсинга (отложено)

Решение принято в пользу кооперативной отмены (§6). Этот раздел — результат
проведённой проверки; он нужен, если позже потребуется мгновенная отмена или
если зависший парсинг станет реальной проблемой в проде. Здесь же лежит факт,
который **нужен уже сейчас** — про осиротевший `soffice` (см. P0-3).

**Убивать воркера текущего `ProcessPoolExecutor` нельзя.** Проверено на этой
машине (Python 3.12, Linux): пул из двух воркеров, две задачи, `SIGKILL` одному
воркеру →

```text
long      -> BrokenProcessPool: A process in the process pool was terminated abruptly...
other     -> BrokenProcessPool   <- соседняя задача, которую никто не трогал
new task  -> BrokenProcessPool: the process pool is not usable anymore
```

Гибель одного воркера уносит все параллельные задачи и ломает пул навсегда.
`future.cancel()` не помогает — он отменяет только не начавшиеся задачи. Это же
объясняет, почему P0-1 обязателен при `prefetch=3`: тот же эффект даёт OOM-killer,
без всякого нашего участия.

**Что сработало бы: отдельный процесс на задачу + убийство группы процессов.**
Второй проверенный факт — про «внуков». Воркер парсинга порождает `soffice`
(`convert_doc_to`, `parser/v1/utils.py:141`). Если убить только воркера,
`soffice` остаётся сиротой:

```text
A: внуков до kill: 1 | процесс жив? False | внуков после terminate(): 1   <- утечка
B: внуков до kill: 1 | процесс жив? False | внуков после killpg():   0   <- чисто
```

Разница: в случае B дочерний процесс первой строкой делает `os.setsid()` (своя
группа процессов), а родитель бьёт по **группе** через `os.killpg`, а не по
одному pid. `soffice`, запущенный обычным `Popen`, наследует группу и умирает
вместе с ней.

**Это применимо прямо сейчас, вне отмены.** Таймаут для `soffice` (P0-3) обязан
убивать группу, а не только прямого потомка: `subprocess.run(..., timeout=)`
прибьёт сам `soffice`, но не то, что тот успел породить. Правильно:
`Popen(..., start_new_session=True)` + `os.killpg` по таймауту.

Если когда-нибудь понадобится полноценное прерывание парсинга, эскиз такой:

```python
ctx = multiprocessing.get_context("forkserver")   # forkserver с preload docling:
proc = ctx.Process(target=_entrypoint, ...)       # spawn заново импортирует docling (секунды)
# в _entrypoint первой строкой: os.setsid()
os.killpg(os.getpgid(proc.pid), signal.SIGTERM)   # затем grace, затем SIGKILL
```

Подводные камни, выявленные при проверке: гонка на старте (родитель может успеть
убить процесс до `setsid`, и `killpg` выстрелит по группе всего сервиса — нужна
проверка `os.getpgid(pid) == pid` перед выстрелом); `fork` напрямую из
asyncio-приложения брать нельзя (форк с работающим event loop и захваченными
локами даёт дедлоки); после `SIGKILL` в ребёнке не отработает ни один `finally`,
поэтому временные файлы должны лежать в каталоге на задачу, который сносит
родитель.

Альтернатива своей реализации — библиотека `pebble` (`ProcessPool` с
`future.cancel()` и таймаутами, пул сам поднимает воркера взамен убитого).
Проблему осиротевшего `soffice` она не решает — `os.setsid()` прописывать
придётся так же.
